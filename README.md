# se-slides — shared slide machinery of the Software Engineering group

A Quarto extension plus build tools for lecture slides with runnable Java code. Every course repository
includes this repository as a Git submodule at `_extensions/se-slides`.

What it gives a course:

- slides in Markdown (Quarto, reveal.js) as HTML and PDF, plus a self-contained Moodle bundle
- code listings from real files with the file's line numbers, a copy button and *Open in VS Code*
- program output, jshell transcripts and compiler errors generated by the build, never typed
- question slides: code → output → answer, step by step
- quality gates: code must compile, images need alt text and credits, layout problems are reported
- the group's look: fonts, colours, logo, favicon

## New course

```powershell
git clone https://github.com/se-buw/se-slides.git C:/teaching/se-slides
C:/teaching/se-slides/tools/bootstrap.ps1                      # once per computer: Quarto and JDK 25
C:/teaching/se-slides/tools/new-course.ps1 -Path C:/teaching/se1 -Title "Software Engineering" -Repo se1
cd C:/teaching/se1
./build.ps1 01 -Preview
```

`new-course.ps1` copies `template/` (example deck, example code, build scripts, VS Code settings,
GitHub workflow), replaces the course title and repository name, runs `git init` and adds this
repository as submodule. Then create the repository `se-buw/se1` on GitHub and push.

## Setup on a new computer

```powershell
git clone --recurse-submodules https://github.com/se-buw/<course>.git
./<course>/_extensions/se-slides/tools/bootstrap.ps1
```

`bootstrap.ps1` downloads the pinned Quarto and the latest Temurin JDK 25 into one shared tool cache
(`%LOCALAPPDATA%\se-slides`, or `$env:SE_SLIDES_HOME`); all courses use it. No admin rights needed.

Recommended: VS Code with the *Extension Pack for Java* and the *Quarto* extension. Open the course
with **File > Open Workspace from File… > `course.code-workspace`** (generated by the build): every
lecture's code folder is its own Java project, so lectures may reuse class names. So that VS Code
compiles and debugs with Java 25, add to your **user** settings:

```json
"java.configuration.runtimes": [
  { "name": "JavaSE-25", "path": "C:/Users/<you>/AppData/Local/se-slides/jdk", "default": true }
]
```

## Build (in a course folder)

| Command | Result |
|---|---|
| `./build.ps1 05 -Preview` | live preview of lecture 05 while editing |
| `./build.ps1 05` | HTML of lecture 05 in `_site/lectures/` |
| `./build.ps1 05 -Pdf` | plus `_site/pdf/05-….pdf` |
| `./build.ps1 -Pdf` | all lectures, HTML and PDF |
| `./build.ps1 -Pdf -Moodle` | released lectures, plus `dist/moodle-<date>.zip` (self-contained HTML, PDF, code, index page) |
| `./build.ps1 -Release` | only the lectures in `release.txt`, as on the website (see Publishing) |
| `./build.ps1 -Lenient` | drafting: missing alt text, credits or regions only warn |
| `./build.ps1 05 -Layout` | HTML plus layout report (`_build/layout/05-….txt`; also part of `-Pdf`) |
| `./build.ps1 05 -ShowLayout` | also marks overflowing slides in the HTML and PDF (red outline and label) |
| `./build.ps1 -Strict` | release: also fails on `::: todo` blocks and layout problems |
| `./build.ps1 -Clean` | deletes the build output and makes all code results and screenshots again |

On Linux/macOS/CI: `./build.sh [lecture] [--pdf] [--strict] [--show-layout] [--clean] [--release]`.

The build fails if code does not compile, a program crashes, a jshell snippet fails, a file in
`broken/` compiles, an image has no alt text or no entry in `images/credits.yml`, or an included
region does not exist.

Code results (compiling, running, jshell) and screenshots are made **on demand**. A lecture is built
again only if its code or the build tool changed (`_build/stamps/`); the messages of the last build
are shown again. Delete `_build/` or use `-Clean` to build everything.

### Screenshots of JavaFX programs

A lecture folder with a file `screenshots.txt` gets screenshots of its JavaFX programs, written to
`images/NN-name/screenshots/` and used on slides like any image (alt text required):

```
# name              program        actions
PosterSheet         PosterSheet    size=420x300
PosterSheet-wide    PosterSheet    size=600x300
Registration        Registration   text=Gunta fire="Pottery"
```

- Programs are the `.java` files of the lecture folder and its `fx/` subfolder. The actions (`size`,
  `wait`, `fire`, `text`, `slider`, `select`, `type`, `key`, `click`, `drag`) are listed in
  `tools/FxShots.java`; images are 2x pixels, a second window becomes `name-2.png`.
- JavaFX comes from the lecture's Gradle project (`gradlew javafxModules` copies the jars to
  `build/javafx`) or from `$PATH_TO_FX`, the `lib` folder of a JavaFX SDK. Without JavaFX the build
  warns (`-Strict`: fails) and keeps the existing images.
- A screenshot is taken again only if its line in `screenshots.txt`, its program, the lecture classes it
  uses, the images in `fx/` or `FxShots.java` changed. The hashes are in `screenshots.sha` next to the
  images: **commit it with the images**, then fresh checkouts and CI take nothing and need no display.
- Credits: no `credits.yml` entry. The author is `lecturer.name` and the licence `screenshots.license`
  from `_variables.yml`; the credits slide gets one line for all screenshots.

Layout: a slide whose content runs into the footer, or whose listing is clipped or too wide, is a
layout problem. Three switches, independent of each other:

- `-Layout` (also part of `-Pdf`, `-Moodle` and `-Strict`) checks every deck in a
  headless browser and lists the problems (slide number and title) on the console and in
  `_build/layout/<deck>.txt`. It only reports.
- `-Strict` fails the build if that list is not empty.
- `-ShowLayout` marks the problem slides in the built HTML and PDF with a red dashed outline and a
  label, for fixing them in the browser. The setting is baked into the HTML: rebuild without it
  before presenting. The Moodle bundle never has marks.

The index page (`format: se-slides-html`, a plain web page) lists all lectures: number, title,
subtitle from the front matter, PDF and video links, and a box to open the deck at a slide number
(`lectures/05-loops.html?slide=12`).

## Course layout

```
_quarto.yml               project settings; format: se-slides-revealjs (+ course-specific options)
_variables.yml            course title, semester data, quiz link; never passwords or access codes
index.qmd                 list of lectures, format: se-slides-html (HTML and PDF links)
lectures/NN-topic.qmd     slides of one lecture
code/NN-topic/            examples of that lecture
  X.java                  compilable example (class names may repeat in other lectures)
  X.in                    input for X: the build runs X with it and records the console session
  X.jsh                   jshell snippets: the build evaluates them and records a transcript
  broken/X.java           must NOT compile; the compiler message can be shown on a slide
  warnings/X.java         must compile with a javac -Xlint:all warning, which can be shown on a slide
images/ + credits.yml     images with source and licence
course.code-workspace     VS Code workspace, one Java project per lecture (generated by the build)
_extensions/se-slides/    this repository (submodule)
build.ps1, build.sh       call tools/build.ps1, tools/build.sh of this repository
```

## Writing slides

File paths on a slide are relative to the deck's code folder: in `lectures/05-loops.qmd`,
`CountTiles.java` means `code/05-loops/CountTiles.java` (a full path starting with `code/` also works).

**Listing** with the file's real line numbers, copy button and *Open in VS Code*:

````markdown
```{.java include=CountTiles.java snippet=loop}
```
````

In the Java file, mark the region with `// region loop` … `// endregion`. Alternatives: `lines=5-9`,
or no attribute for the whole file (then the file must not contain region markers).

**Listing with its generated output**, next to it or below it:

````markdown
```{.java include=CountTiles.java snippet=loop output=right}
```
```{.java include=PrintRow.java snippet=loop output=below}
```
````

`split=50` sets the width of the code column in % (default 58).

**Output alone**, **jshell** and **compiler errors**:

````markdown
```{.output of=LoopQuiz.java}
```
{{< jshell while.jsh >}}                  listing and transcript below (output=right / output=none, split=50)
{{< error broken/ForScope.java >}}        compiler message (code=true: also the file)
{{< error warnings/StaticAccess.java >}}  compiler warning of a file in warnings/
````

A program is run if it has an `X.in` file or one of the markers `// @run`, `// @args a b "c d"`
(command-line arguments) or `// @expect-exception` (crashes on purpose). Mark jshell files with
errors on purpose with `// @expect-error`. Marker lines at the start or end of a file are not shown
in whole-file listings. Programs run with an English locale and the time zone Europe/Berlin, so
outputs are the same on every machine. Code is compiled with `-g`, so helpful NullPointerException
messages name local variables. Files in `broken/` and `warnings/` may use the lecture's other classes.
jshell files start with the default imports of interactive jshell (`java.util.*`, `java.util.stream.*`, …).

### Questions and surprising behaviour

Slides that ask a question or show surprising behaviour reveal step by step; all other slides have no
animations. Title the slide as a question and do not give the answer away in the title or in code
comments:

````markdown
## What does this print?

::: question
```{.java include=ExtraSemicolon.java snippet=loop output=below}
```

::: answer
A semicolon too many: ...
:::
:::
````

Inside `::: question`, every generated output appears on the first click and `::: answer` on the
second; the answer is also copied into the speaker notes. `::: {.question answer=right}` puts the
answer in a column next to the rest (`split=55` sets the width of the left column). In the PDF all
steps are shown at once.

### Other building blocks

- `::: tip`, `::: pitfall`, `::: java25` — coloured boxes; `::: {.java25 since=16}` for a modern
  feature from an earlier release (label "Java 16")
- `::: notes` — speaker notes (press `S` in the browser)
- `::: todo` — visible reminder while drafting; fails `-Strict`
- `{{< qr var:quiz >}}` — QR code and link, URL from `_variables.yml` (`size=110` for a smaller code)
- `[{{< qr var:quiz size=110 >}}]{.corner}` — QR code in the top right corner, next to the title
- `{{< var semester.name >}}` — any variable from `_variables.yml`
- Diagrams: ```` ```{mermaid} ```` with `%%| fig-alt: "..."` (flowcharts, class diagrams) or ```` ```{dot} ````
  (Graphviz, `//| fig-alt: "..."`). Diagrams are at most 420 px high; `::: tall` around one allows 560 px.
  Graphviz: set `//| fig-width` / `//| fig-height` to the diagram's aspect ratio (Quarto's default
  box is 960×480) and use `fontname="Jost"` (other fonts are measured too narrow).
- Custom columns: `:::: columns` / `::: {.column width="55%"}`
- Line highlighting steps, only where they help: `code-line-numbers="|3|5-7"` on a listing
- A code block in braces must start with a class (`{.text include=...}`, not `{include=...}`);
  otherwise Quarto treats it as an executable cell

In the browser: `H` or "☰ All lectures" goes back to the list of lectures, `?slide=12` after the
deck's URL opens slide 12, `Esc` shows the slide
overview, `S` the speaker view. "Open in VS Code" uses `vscode://file/<folder>/<file>:<line>`; local
builds use the course checkout's folder, students set the folder of their clone once with the ⚙ button
next to a listing (stored in their browser). VS Code should have `course.code-workspace` open.

## Publishing

The course workflow (`.github/workflows/build.yml`) builds on every push and nightly and deploys
`_site/` to GitHub Pages. With the organisation's Pages domain (se-buw.de), a course repository
`se-buw/<course>` appears at `https://se-buw.de/<course>/`.

- se-slides is public, so the workflow fetches the submodule with its own token. Should it become
  private, create a fine-grained personal access token with read access to `se-buw/se-slides` and
  store it in the course repository as secret `SE_SLIDES_TOKEN`; the workflow uses it when present.
- GitHub Pages from private repositories requires a paid plan (GitHub Team/Enterprise or the free
  education offer); the published site itself is public.

**Through the group website instead** (intro-java: `se-buw.de/teaching/intro-java/slides/`): the course
workflow uploads `_site` as artifact `site` (`actions/upload-artifact`, 90 days) instead of deploying
it, and a job starts the website's workflow with `gh workflow run publish.yaml -R se-buw/se-buw.github.io
-f intro_java_run=$GITHUB_RUN_ID`. The website's build downloads the artifact of that run (or of the
latest successful run, for other website changes) into `static/teaching/<course>/slides/`, which is
git-ignored there. One fine-grained token, stored in both repositories, needs Actions read on the
course repository and Actions read/write on the website repository. The trade-off: the slides are
built once, in the course repository, where the build is also the check, and website changes stay
fast; but the website depends on an artifact that expires (the nightly course build renews it).
Building the slides in the website's workflow would need no artifact, but would add Quarto, Java and
all PDFs to every website deploy.

### Releasing lectures one by one

`release.txt` in the course folder lists the released lectures, one per line (`05` or `05-loops`,
`#` comments). Without the file every lecture counts as released.

- `./build.sh --release` / `./build.ps1 -Release` build only these lectures, and the lecture list on
  the index page shows only them. The workflow builds with `--release`, so the website has only
  released lectures. Without the flag (your local builds) everything is built and listed.
- `-Moodle` implies `-Release`: the bundle has the released HTML, PDF and code, with a
  `course.code-workspace` for the students and without build output.
- `java _extensions/se-slides/tools/BuildCode.java --export-code DIR [lecture ...]` copies the
  git-tracked files of the released lectures' `code/` folders to `DIR/code/`, and writes a students'
  `course.code-workspace` and a `.gitignore`.

**Students' code repository.** A job `publish-code` in the workflow exports the released code to a
public repository (e.g. `se-buw/<course>-code`) and commits only when something changed ("Release
06-methods" when a lecture is added). Set `repo-url` in `_quarto.yml` to that repository for "web"
links next to listings (`<repo-url>/blob/main/code/...`); exclude it from the link check, since new
files arrive there only after the check. Setup once:

1. Create the repository with an initial commit on `main`.
2. `ssh-keygen -t ed25519 -N "" -f deploy-key`: add `deploy-key.pub` to the code repository as
   deploy key with write access, and the private key `deploy-key` to the course repository as secret
   `STUDENT_CODE_DEPLOY_KEY`. Delete both files afterwards.

## Recording lectures

Lectures recorded with OBS and uploaded to YouTube (public or unlisted) get chapters in the video and
a "▶ Video" link on every slide (key `Y`) that opens the recording where the slide was explained.
Nothing changes in the `.qmd` files and there is nothing to press during the lecture: each deck logs
its slide changes with the time in the browser, and OBS names a recording after its start time.

After the lecture, in a course folder:

1. In the deck you presented, press **Shift+R**: the browser saves the log as
   `slidelog-<date>.json` to Downloads.
2. `./video.ps1 05`: prints the YouTube chapters and copies them to the clipboard.
3. Upload the recording in YouTube Studio and paste the chapters into the description.
4. `./video.ps1 05 -Id <link>`: writes the video ID into `lectures/05-….video.json`. Commit it; the
   build adds the links to the slides, the lecture list and the Moodle index.

How the times are found:
- **Recording window:** the start comes from the OBS file name (the default
  `2026-10-14 10-15-03.mkv`). The end is start + length (with `ffprobe` installed) or else the
  file's last change. Recordings are looked for in your Videos folder; use `-RecordingDir` or
  `COURSE_RECORDINGS` for another folder, or `-Recording <file>`. `-Start`/`-End` set the window by
  hand.
- **What is ignored:** going through the slides before or after the recording. The slide on screen
  when the recording starts counts from 0:00.
- **Longest visit:** a slide links to its longest visit, so flipping through slides, previewing one
  and short recaps don't move the link. A reload or a closed and reopened deck doesn't split a visit.
- **Other decks:** switching to another deck in between is fine.
- **Several recordings:** a lecture recorded in several files (OBS restarted, or two sessions) gets
  one video per file. `-Id` takes their links in recording order.
- **Chapters:** each section and each slide shown for at least 60 s (`-MinChapter`). A slide the
  lecture comes back to gets `↩`.
- **Running it again** is safe: video IDs are kept. `-Id` also corrects IDs.

Don't pause the recording (it shifts all later times; stop and start a new one instead), don't
present in a private window (its log is gone when it closes) and export the log within 14 days.
The log is stored per site: export it from the place you presented from (`file://`, Pages,
preview).

## Changing se-slides

Edit inside any course checkout (`_extensions/se-slides` is a normal Git repository), test with that
course, commit and push from there. A submodule is checked out on a detached HEAD, so first run
`git -C _extensions/se-slides switch main` (and `git pull`), otherwise the commits are on no branch. Other courses pick up the change with
`git submodule update --remote _extensions/se-slides`. Bump `version` in `_extension.yml` for
noticeable changes.

Pinned tool versions: `tools/bootstrap.ps1` (Quarto) and `template/.github/workflows/build.yml` (also
in each course's workflow).
